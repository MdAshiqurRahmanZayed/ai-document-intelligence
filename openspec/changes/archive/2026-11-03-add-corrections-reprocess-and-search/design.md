# Design

## Context

Read from the code: `services/documents.py` already holds the pattern reprocess needs (claim a document with a conditional `UPDATE … WHERE status = …`, then hand it to the broker through an injected `enqueue`, marking it `FAILED` with `queue_unavailable` if the broker refuses). `app.state.enqueue` queues only the ingest job. The extraction service (`services/extraction.py`) already has `validate_document`, duplicate lookups and `route`, and `extractions` rows carry `is_current`, a per-document `version` and denormalized lookup columns (`invoice_number`, `supplier_norm`, `invoice_date`, `total`, `currency`). `pgvector` is enabled (migration `0001`) and every Postgres image used is `pgvector/pgvector:pg16`. The `embed` queue exists and `GoogleGenerativeAIEmbeddings` comes with `langchain-google-genai`, which is already installed. The extraction job does not set `PROCESSING` itself (ingest does). See `proposal.md` for motivation and `specs/` for requirements.

## Goals / Non-Goals

**Goals:**
- Reuse the existing validation and normalization code for corrections, and the existing claim-then-queue pattern for reprocessing.
- Keyword search that works with no model and no key; semantic and hybrid search as additions on top.
- One filter implementation shared by the list and search.
- A cut order that leaves a coherent system if time runs out.

**Non-Goals:**
- Frontend, SSE, rate limiting, user accounts, search tuning (see proposal).

## Decisions

**D1. Layout.** Services: `corrections.py`, `reprocess.py`, `listing.py` (filters, cursor, invoice summaries), `indexing.py` (chunks and embedding writes), `search.py`. `app/llm/embeddings.py` holds `EMBEDDING_DIM = 768`, an `Embedder` protocol (`embed_documents`, `embed_query`) and `build_embedder(settings)`, mirroring `build_extractor` so tests inject a fake. `app/api/auth.py` holds the key check. Routes: corrections, corrections list and file link in `documents.py`; new `jobs.py` and `search.py`. Nothing under `services/`, `llm/`, `validation/` imports FastAPI.

**D2. A correction is a new version of one invoice.** The editable fields are validated as a set (unknown field: 422). The current invoice's values are turned back into an `InvoiceDraft` of strings, the patch is laid over it (a `null` clears a field; `line_items` replaces the list), and `normalize_invoice` runs on it, so an edit follows exactly the rules of extracted values and an unreadable value is a 422 naming the field. Grounding is not applied: a person's value is authoritative. The new `Extraction` row has `version = latest version of that invoice + 1`, `is_current = true`, `model = "manual"`, `prompt_version = "manual"`; the previous row of that invoice is set not current. Confidence: copied from the old row, set to 1.0 for edited fields and dropped for fields now null; `grounding` (quotes) copied except for edited fields. The denormalized columns are refreshed from the new data. Versions are unique per invoice (`(document_id, invoice_index, version)`), and the extraction job's "next version of the document" rule still yields unique numbers, so reprocessing after corrections is safe. If the normalized result equals the current data, nothing is saved (200).

**D3. Audit table.** `corrections(id, document_id, extraction_id, field, old_value, new_value, edited_by, created_at)`: `extraction_id` is the new version, values are text (the string form of a scalar, JSON for `line_items`, `NULL` for empty), one row per field whose normalized value changed, index `(document_id, created_at)`. Old versions stay in `extractions`, so the audit trail can be replayed.

**D4. Re-validation reuses the rules, per invoice.** `validate_document` rebuilds findings for every invoice it is given, which would drop the other invoices' grounding warnings (those are saved as findings, not recomputed). So the validation code is split in two: `validate_invoice_findings(session, document, record, …)` (rules, normalization warnings, duplicates for one invoice, replacing that invoice's findings) and `document_status(session, document_id)` (reads every finding of the document's current invoices plus document-level findings and applies `route`). The extraction job calls both for all invoices; a correction calls the first for the edited invoice only and the second for the document. A correction therefore clears warnings that belonged to the replaced version (for example `ungrounded_field` for a field now set by hand), which is intended. The edited invoice's duplicate check runs against other documents' current invoices, as in extraction.

**D5. Reprocess claims, then queues.** `reprocess.py` runs `UPDATE documents SET status='QUEUED', error_code=NULL, error_message=NULL WHERE id=:id AND status IN ('FAILED','NEEDS_REVIEW','COMPLETED') RETURNING id` and commits; no row means `already_queued` (409), which also makes simultaneous requests safe. It then calls an injected enqueue (`app.state.enqueue` for `ingest`, a new `app.state.enqueue_extract` for `extract`) in a thread and, if that raises, marks the document `FAILED / queue_unavailable` like uploads do. Stage `extract` is checked before the claim: Google key configured (`extraction_disabled`) and at least one page with text (`no_text`). Because the extraction job did not set `PROCESSING` itself (ingest did), `_run_extract` now sets it when it starts, so a re-extraction shows `QUEUED` then `PROCESSING` like every other job. Reprocessing keeps events, earlier versions and corrections; a re-extraction produces a new current version from the model, so manual edits stop being current (documented, and recoverable from the audit trail).

**D6. Bulk retry.** `retry-failed` selects `FAILED` documents oldest first (limit), picks the stage per document (`extract` when `error_code = 'extraction_failed'` and extraction is possible, otherwise `ingest`), and runs the same claim-then-queue for each; the response lists queued ids and counts the ones that could not be queued. It is a loop over D5, so it inherits its safety.

**D7. Listing and filters.** One function builds the document filters and is used by the list and by search. Invoice filters are a single `EXISTS` over current extractions that must satisfy all of them together (spec). Supplier filter: `supplier_norm LIKE %normalize_name(q)%` (with `%` and `_` escaped). Invoice number: compared by the same alphanumeric key that cross-verification uses, computed in SQL (`lower` and `regexp_replace`). Dates and amounts use the `invoice_date` and `total` columns. Pagination is keyset on `(created_at DESC, id DESC)`; the cursor is the URL-safe base64 of `[created_at ISO, id]`; the page is fetched with `limit + 1` rows to know whether a next page exists. Invoice summaries for the page come from one query on current extractions, ordered by document and invoice index. Alternative: offset pagination; rejected, it drifts when new documents arrive.

**D8. Chunks.** Table `chunks(id, document_id, page_no, chunk_no, text, tsv, embedding, created_at)`: `tsv` is a generated, stored column `to_tsvector('simple', text)` (no stemming or language guess, so Swedish and English invoices behave the same), `embedding` is `vector(768)` and nullable, unique `(document_id, page_no, chunk_no)`, GIN index on `tsv`, HNSW index on `embedding vector_cosine_ops`, index on `document_id`. Chunking uses `RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=150)` per page (from `langchain-text-splitters`; plain Python would do, this is the planned thin LangChain use). `index_chunks` deletes the document's chunks and inserts the new ones inside the caller's transaction.

**D9. When indexing happens.** In `_run` (ingest) when no OCR is pending, and in `_run_ocr`, `index_chunks` runs before the final commit of that job, so a document never completes without its chunks, and an indexing error retries the (idempotent) job. After the commit, with a key configured, `embed_document` is queued on the `embed` queue (`rate_limit="60/m"`, same retry policy). It embeds the chunks that have no embedding in batches of 50 (`asyncio.to_thread` around the blocking call), committing per batch, and writes `embed` events. Its `on_failure` only records a failed event: it does not change the document status. The embedding job is independent of extraction; both are queued once the text is ready.

**D10. Vector type without a driver codec.** asyncpg needs a codec to bind pgvector values. Rather than registering one on every engine (the API, each worker task and the tests create their own), the column uses a small `UserDefinedType` for `vector(768)` that sends the value as text and casts it in SQL (`CAST(:v AS vector)`), and queries use `embedding <=> CAST(:q AS vector)` through SQLAlchemy `text`/`func` expressions. The asyncpg dialect already sends strings with an explicit text cast, so the double cast works. If this meets friction, the fallback is the `pgvector` package with its asyncpg registration on connect; the tests against the real database decide. The dimension is a constant (`EMBEDDING_DIM = 768`) used by the migration, the model and the embedder (`output_dimensionality=768`), and a test asserts that model and constant agree; changing it needs a new migration.

**D11. Embedding model.** `EMBEDDING_MODEL` (setting, default `models/gemini-embedding-001`, a placeholder to verify at the first real run) through `GoogleGenerativeAIEmbeddings` with `task_type` `retrieval_document` for chunks and `retrieval_query` for queries, `output_dimensionality=768`. Tests use a fake embedder: deterministic word-hashing vectors padded to 768 dimensions, with a tiny synonym table so a "meaning" test is possible without a model.

**D12. Search.** `GET /search` takes `q`, `mode` (`hybrid` default), `limit` and the list filters. All three modes first restrict chunks to documents matching the filters (`chunks.document_id IN (SELECT id …)`). Keyword: `websearch_to_tsquery('simple', q)` against `tsv`, rank `ts_rank_cd`, top 50 chunks. Semantic: embed the query, `WHERE embedding IS NOT NULL ORDER BY embedding <=> :q LIMIT 50`, score `1 - distance`. Hybrid: take both top-50 lists, give each chunk `Σ 1/(60 + rank)`, sort. In every mode the chunks are reduced to the best chunk per document (in Python, order preserved), cut to `limit`, and the invoice summaries are attached with the listing query. Snippets: keyword uses `ts_headline` with private-use marker characters, then the server HTML-escapes the whole string and swaps the markers for `<mark>`/`</mark>`, so the snippet is safe to render as HTML (the text comes from uploaded files). Semantic and hybrid results without a keyword match use the first 200 characters of the chunk, escaped. Without a key: `semantic` is a 409 `semantic_unavailable`; `hybrid` runs as keyword and says so in `mode_used`.

**D13. API key.** Setting `API_KEY` (`SecretStr`, optional). `require_api_key` is a FastAPI dependency added to every router under `/api/v1` when the routers are included (`include_router(..., dependencies=[…])`); it reads `X-API-Key`, compares with `secrets.compare_digest`, and raises 401 `Invalid or missing API key`. `/healthz`, `/readyz` and `/docs` are outside `/api/v1`. CORS middleware answers browser preflight requests before routing, so they never reach the check (a test pins this, with the header `X-API-Key` allowed by `allow_headers=["*"]`). Without a key the app logs `auth_disabled` at startup. The key is never logged (settings are already dumped masked at startup). Alternative: JWT users; rejected, no accounts exist and the assignment does not need them. `edited_by` is therefore free text from the request.

**D14. Tests.** Pure parts (cursor encoding, normalization of filters, RRF, snippet escaping) are unit tests. Services, endpoints and the migration run against the real test database (the test image has pgvector). Embeddings and the extraction model are fakes injected where the code builds them (`build_embedder`, `build_extractor`); the `API_KEY` tests build the app with a settings object that has a key.

## Risks / Trade-offs

- [The custom vector type misbehaves with asyncpg] -> Tests on the real database come first in the embeddings group; fallback to the `pgvector` package with codec registration (D10).
- [Embedding model ID or dimension is wrong] -> Setting plus constant; a failing embed job only records an event, keyword search keeps working; verified in the real-model run.
- [A correction drops warnings of the old version (for example `ungrounded_field`)] -> Intended: the person has replaced the value. Documented.
- [Reprocess from extraction discards manual corrections as the current version] -> Documented in the API docs; the audit trail and older versions remain.
- [Snippet markup from uploaded documents could inject HTML into a client] -> Server-side escaping with marker characters, pinned by a test (D12).
- [Single shared API key, no rate limit] -> Enough for the assignment; rate limiting and per-user keys are listed as hardening work.
- [Keyword search with the `simple` configuration finds exact words only] -> Chosen for predictable behaviour across languages; semantic search covers fuzzy meaning.
- [`LIKE`/`regexp_replace` filters do not use indexes] -> Fine at this scale; the denormalized columns and a trigram index are the next step if lists grow large.

## Migration Plan

Add the dependency, add `API_KEY` (optional) and `EMBEDDING_MODEL` to `.env`, run `make migrate` (migration `0003` creates `corrections` and `chunks` with their indexes), and rebuild the images. Documents processed before this change have no chunks: `POST /jobs/…` does not cover that, so a one-off shell call `index_chunks` plus `embed_document.delay(<id>)` per document backfills them (or reprocess them from `ingest`). Rollback: revert the code and run `alembic downgrade 0002`; chunks are derived data, corrections are lost with the table.
