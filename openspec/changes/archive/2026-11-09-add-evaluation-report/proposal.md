# Proposal

## Why

Task 7 of the assignment and deliverable 7 require an evaluation on a labelled dataset that reports actual extraction accuracy, processing time, document success rate and failure rate. None of this exists: there is no labelled dataset, no accuracy figure, no success or failure rate, `make eval` is a placeholder, and the README says the evaluation was not done. The only timing figures (`docs/performance.md`) come from generated one-line pages with an in-memory storage double. No real labelled data is available, so the evaluation uses a labelled synthetic dataset with known true values, generated by code, and says so in the report.

## What Changes

- Add a labelled dataset: about 33 documents built by `eval/build_dataset.py` from known values, sized to fit a limited model quota and covering digital PDFs, scanned PDFs, JPG/PNG/TIFF at several quality levels, spreadsheets (CSV, XLSX, XLS, several sheets), multi-invoice PDFs, invoices with fields deliberately absent, invoices with seeded validation errors and duplicates, and files that must be refused or fail (encrypted, corrupt, empty, renamed). Ground truth and the expected outcome of each file are committed; the generated documents are not.
- Add an evaluation runner, `eval/run_eval.py`, that sends the dataset through the real API and pipeline with the real model, waits for each document to finish, and records outcome, end-to-end time and per-stage time. The run can be limited to a group of files and resumed from saved results, so a quota limit or an interruption does not repeat model calls.
- Add scoring (`eval/scoring.py`): per-field accuracy with wrong, missing and invented values counted apart, document exact match, invoice count, validation detection and false alarms, success and failure rates, and time percentiles by file type and stage.
- Add a committed report, `eval/results/report.md`, with raw results in `eval/results/results.json`, recording the model IDs, prompt version, dataset, date and commit, a failure analysis from the actual results, and the limits of a synthetic dataset.
- Implement `make eval` (it prints "not implemented" today) and a way to rebuild the report from saved results without calling the API.
- Replace the README's "no evaluation" limit with the measured results, and document the dataset and how to extend it with real labelled documents.
- Add tests for the scoring, the runner (against a stub API) and the report rendering.

Out of scope: a larger dataset (the format and builder allow one, but it costs more model calls than the available quota), changing the prompt, model or validation rules to raise the scores (the set is not used for tuning, and any such change is a separate change), building a real-world dataset (the format allows adding one), evaluating cross-verification, load testing at 1000 pages end to end (`docs/performance.md` keeps its ingest figures), and UI changes.

## Capabilities

### New Capabilities
- `evaluation`: a labelled dataset, a runner that measures extraction accuracy, success and failure rates and processing time through the real pipeline, and a committed, reproducible report.

## Impact

- New directory `eval/` (dataset builder, ground truth, scorer, runner, results, README) and `eval/tests/`.
- `backend/scripts/make_sample_documents.py` is refactored so its drawing and invoice helpers can be reused; its output stays the same.
- `Makefile` (`eval` target), `docker-compose.yml` (a read-only mount of `eval/` into the backend test container), `README.md`, `docs/testing.md`.
- The run needs the stack up, an empty database and a working `GOOGLE_API_KEY`; it makes real model calls (about 25 to 30 extraction calls plus embeddings for the dataset), so it is run by hand, never by `make test`.
- No API, schema or runtime behaviour changes.
